# Product Domain Specification v2
# دستیار هوشمند کسب‌وکارهای مجازی

Status: Draft for review / approval
Version: 2.0
Date: 2026-09-12

## 1. Purpose

Product Domain هویت و وضعیت داخلی یک محصول قابل فروش را مستقل از ساختار Excel/Google Sheets و مستقل از پست‌های منتشرشده نگه می‌دارد.

اصل پایه:
- Source format is input, not identity.
- Row number/order is never identity.
- Product facts, AI content, Post content and remote publication state are separate concerns.
- Product state must remain durable, compact, explainable and recoverable.

## 2. Scope

Product Domain must support:
- Excel and Google Sheets as initial sources.
- Arbitrary source column names/order/extra fields.
- Customer-enabled/disabled columns.
- Suggested field mapping + manual correction + final confirmation.
- Stable internal Product identity even when source rows move/disappear/reappear.
- Customers with or without explicit product IDs.
- Product media management from the customer/admin panel.
- Standard and business-specific fields.
- Typed custom attributes such as touch, refresh_rate, color, size, etc.
- Product versions and compact change metadata.
- Data-quality checks and error isolation.
- AI outputs associated with products, without allowing AI to alter canonical facts.
- Default and versioned Presets consuming product fields.
- Publication/reconciliation references without making Product equal to Publication.

Out of scope for this domain:
- Direct customer order management.
- Full CRM.
- Autonomous business decisions.
- Product mutation inside source files by the system.
- Platform-specific API implementation details.

## 3. Product identity

### 3.1 Immutable internal identity

Each Product has an internal immutable `product_id` generated by the system.

The following are NOT product identity by themselves:
- row number
- row order
- display name
- price
- stock
- image URL
- arbitrary source locator

### 3.2 External identity hints

When available, the system may use:
- customer product ID
- SKU
- barcode
- external catalog ID
- reliable source key

These are identity evidence, not automatically trusted forever. A customer can change an identifier and the system must distinguish identifier change from creation of a new Product.

### 3.3 Identity resolution priority

1. Explicit stable ID with validated continuity.
2. Reliable source/external key.
3. Business/source-specific deterministic composite identity.
4. Controlled similarity/fingerprint matching.
5. Manual review for ambiguity.

Name-only matching is prohibited as a confident identity rule.

### 3.4 Identity outcomes

- EXACT_MATCH
- CONFIDENT_MATCH
- NEW_PRODUCT
- POSSIBLE_DUPLICATE
- AMBIGUOUS
- UNRESOLVED
- IDENTITY_CONFLICT

AMBIGUOUS, UNRESOLVED and IDENTITY_CONFLICT must not silently merge products.

False merge is more dangerous than false-new-product.

## 4. Source Record

A Source Record represents the current representation of an item in an external source.

Conceptual data:
- `source_record_id`
- `source_id`
- source-specific locator/reference
- optional external key
- current `product_id` resolution
- source fingerprint
- last_seen timestamp
- source-record state
- mapping_version used for interpretation

A Source Record can disappear while its Product remains known.

A Source Record can move to a different row/location without changing Product identity.

Source Record must never be used as the sole historical identity of the Product.

## 5. Product lifecycle

Conceptual lifecycle states:

- DISCOVERED
- ACTIVE
- MISSING_FROM_SOURCE
- SUSPICIOUS_CHANGE
- REVIEW_REQUIRED
- ARCHIVED
- RESTORED

The exact transition state machine is part of the approved domain design.

### 5.1 Missing source data

A product missing from one source read is NOT automatically deleted.

Possible causes:
- actual deletion
- temporary source outage
- permission loss
- partial read
- changed sheet/range
- source filtering
- mapping problem
- customer reorganized the source

Default V1 behavior:
- preserve Product
- mark it as missing/non-destructive
- do not immediately delete remote publications
- do not purge Product history
- re-check/reconcile according to source policy

Destructive unpublish requires an explicit policy and adequate confidence.

### 5.2 Reappearance

When a missing Product reappears:
1. resolve identity
2. verify source data
3. compare with last known state
4. update Product if safely matched
5. determine downstream publication changes
6. prevent duplicate publications

## 6. Product creation and source re-creation

If a customer deletes a source row and creates a new row:

- If a stable identifier proves continuity, reconnect to the existing Product.
- If no identifier exists, run identity resolution.
- If evidence is ambiguous, create a reviewable case.
- If confidently new, create a new Product.

The system must never assume that visually similar rows represent the same product merely because the customer recreated them.

## 7. Recommended source structure

The platform supports arbitrary structures, but onboarding MUST provide a recommended structure per Business Type.

Example laptop template:
- product_id
- name
- brand
- model
- cpu
- ram
- storage
- gpu
- touch
- price
- stock
- description
- image_1
- image_2
- image_3

The recommended template is guidance, not a hard technical requirement.

The customer should be encouraged to:
- use a stable product ID
- avoid reusing IDs
- avoid unnecessary row churn
- keep one product per logical record
- avoid duplicate products
- preserve predictable column meanings

The system must still remain resilient when the customer does not follow these recommendations.

## 8. Source onboarding and mapping

Required flow:

Source → detect structure → customer selects enabled columns → proposed mapping → customer review → manual correction → validation → final confirmation → mapping activation.

### Rules

- Disabled columns do not enter the downstream product pipeline.
- Unknown columns remain inert until explicitly mapped/enabled.
- Customer confirmation is required before activation.
- Mapping profiles are reusable.
- Mapping is versioned.
- Mapping changes must never silently reinterpret historical Products or Posts.
- Significant mapping changes may require a new validation/review step.

## 9. Mapping confidence and evidence

Each proposed mapping should have:
- source column
- proposed canonical field
- confidence
- evidence/reason
- validation result

Example:

`"قیمت فروش" -> price`

Confidence: 0.98
Evidence: numeric values + semantic column-name match + currency pattern.

The system must be able to explain mapping decisions in logs.

AI may assist mapping suggestions, but customer confirmation is authoritative.

## 10. Data quality and error isolation

Import must classify rows without unnecessarily blocking valid products.

Example result for 5000 rows:

- 4978 valid
- 15 warnings
- 7 blocked

A small number of invalid rows must not automatically fail the whole import.

Data-quality outcomes may include:
- VALID
- WARNING
- BLOCKED
- DUPLICATE_CANDIDATE
- IDENTITY_AMBIGUOUS
- INVALID_REQUIRED_FIELD
- INVALID_TYPE
- INVALID_MEDIA
- INVALID_REFERENCE

The system must preserve enough information to tell the customer/admin what needs correction without exposing internal stack traces as user-facing messages.

## 11. Canonical Product model

### 11.1 Core fields

The canonical model should contain a small stable set of common concepts, such as:
- product_id
- business_id
- product name
- category/type
- description
- price
- currency
- stock status
- external identifiers
- lifecycle state
- current version reference
- timestamps

### 11.2 Custom typed attributes

Business-specific attributes must not require a schema migration for every new field.

Example:

`attributes.touch = boolean`

`attributes.refresh_rate = number`

`attributes.ram_type = string/enum`

Each custom attribute may have metadata:
- key
- display name
- type
- validation rules
- allowed values
- required/optional flag
- template exposure rule
- formatting rule

## 12. Template exposure

Any approved Product field can optionally be exposed to the template engine.

Examples:
- `{product_name}`
- `{price}`
- `{stock}`
- `{touch}`
- `{cpu}`
- `{ai_description}`
- `{ai_recommendation}`

Presentation rules can transform values:
- true → دارد
- false → ندارد
- yes → بله
- no → خیر
- numeric values → formatted display

The renderer must support missing/empty values without producing broken output.

## 13. Product media

Media is a first-class Product component, not a single `image_url` field.

A Product may have zero, one or many media items.

Conceptual media metadata:
- media_id
- product_id
- media type
- source (customer/source/system)
- reference/storage key
- order/position
- fingerprint/hash
- availability/status
- created_at
- updated_at

Customer/Admin capabilities in V1:
- add media
- remove media
- replace media
- reorder media when applicable
- preview media

Media changes must be classified so the publication layer can decide whether edit, replacement or repost is required per platform.

The Product domain does not assume all platforms support albums or multiple-media edits.

## 14. Product versions

A ProductVersion represents a material canonical state.

Storage must remain compact.

Do NOT store a full snapshot on every sync.

Preferred model:
- current canonical state
- version number
- changed field/category metadata
- compact hashes/fingerprints
- previous version reference where needed
- full historical snapshot only when explicitly required for recovery/audit/high-risk rules

Change categories may include:
- NAME_CHANGED
- PRICE_CHANGED
- STOCK_CHANGED
- DESCRIPTION_CHANGED
- MEDIA_CHANGED
- SPECIFICATION_CHANGED
- CATEGORY_CHANGED
- CUSTOM_FIELD_CHANGED
- IDENTITY_IDENTIFIER_CHANGED

## 15. Change risk

Risk is Business Type and field aware.

Suggested baseline:
- LOW: presentation-only/description changes
- MEDIUM: price/stock changes
- HIGH: technical specifications
- CRITICAL: identity/external identifier changes

Risk determines validation/review behavior; it does not automatically mean every change is blocked.

Example laptop:
- CPU → HIGH
- GPU → HIGH
- RAM → HIGH
- Price → MEDIUM
- Stock → LOW

Example clothing:
- Size → HIGH
- Color → HIGH
- Price → MEDIUM
- Stock → LOW

## 16. Suspicious changes

A change may be suspicious when:
- a high-risk field changes unexpectedly
- many products change the same field at once
- source structure changed simultaneously
- values become invalid
- a product appears to switch identity
- a mapping was recently changed

Suspicious changes should be isolated/quarantined according to policy instead of blindly propagating them to every platform.

## 17. Sync semantics

Every sync should distinguish:
- source state
- resolved Product state
- changes detected
- actions required
- actions blocked
- unresolved records

Repeated sync of identical source content must be idempotent:
- no Product churn
- no unnecessary ProductVersion
- no duplicate downstream jobs
- no AI regeneration
- no duplicate publication

## 18. AI content relationship

AI output is an editorial artifact, not a Product fact.

Example:

Product facts:
- cpu = i7
- ram = 16GB

AI artifacts:
- ai_description
- ai_recommendation

AI must never silently change canonical facts.

### 18.1 AI output definitions

AI outputs are configuration-driven and versioned.

Each definition may contain:
- key
- display name
- prompt/system instructions
- required input fields
- expected output schema
- validation rules
- length limits
- token/cost policy
- enabled state
- version
- allowed template exposure

Example:
- `ai_description`
- `ai_recommendation`

### 18.2 AI reuse rule

If an approved AI artifact already exists and its dependencies remain valid, reuse it.

Previously published content MUST NOT automatically receive fresh AI generation because a prompt/model changed.

Manual regeneration requires explicit user/admin action and permission/credit checks.

## 19. Manual editing of AI output

Customer/Admin may edit generated AI output before approval and after it has been stored.

The system should distinguish:
- generated
- edited
- approved
- rejected
- stale
- superseded

The approved artifact becomes the reusable source for future publication where applicable.

## 20. Product-to-Post separation

Product is not Post.

Product holds facts and media.

Post holds a versioned rendered representation.

Publication represents the relationship between a PostVersion and a specific platform/channel.

Conceptual relationship:

Business → Product → ProductVersion → Post/PostVersion → Publication → PublicationAttempt

A Product may have multiple Post/Publication representations across platforms.

## 21. Remote manual editing policy

A customer or channel admin may modify a published message outside the platform.

That remote edit must NOT modify Product facts.

V1 principle:
- distinguish system-managed content from user-owned content
- update only system-managed parts where technically possible
- preserve unrelated manual changes where possible
- never treat remote message changes as a Product edit

Platform limitations may require full re-render/republication. That decision belongs to the Publication/Platform layer.

## 22. Default Preset relation

Every Business Type/business configuration must have an Admin-defined default Preset.

If a customer has not selected a Preset, the default is used.

Presets are versioned.

A Preset change must not rewrite historical Posts or automatically trigger AI generation for already-published Products.

Pending jobs must hold an explicit Preset version reference.

## 23. Product media vs source media

Source images and manually added media are separate origins.

The system should retain enough metadata to determine whether a source sync is allowed to replace/remove customer-added media.

Default safety principle:
- source refresh should not silently destroy manually managed media unless the customer explicitly configured that source as authoritative.

## 24. Business type change

Changing Business Type must not automatically destroy Product data.

Two cases:

### Correction of wrong classification

If the customer selected the wrong Business Type but the underlying Business remains the same:
- Business identity remains
- Product identity remains
- compatible fields are retained
- incompatible field configurations are revalidated
- templates/mapping/risk policies may require review

### Actual new business

If the customer is effectively creating a separate business:
- create a new Business identity
- retain the old Business as archived when appropriate
- do not mix Products, Sources, Publications, Admin memberships or settings across the two businesses

Product reassignment between businesses is a separate high-impact workflow and is not implied by changing a business type.

## 25. Subscription and entitlement relationship

Product processing is constrained by the active Business subscription.

Examples of potential limits:
- maximum products
- maximum sources
- maximum connected channels
- sync frequency
- AI credits
- media/storage quota
- operation quota

Entitlement checks must occur before expensive or externally visible work.

Subscription expiry must not corrupt Product state. Products should remain durable even when publishing is temporarily blocked.

## 26. Admin/customer permissions over Products

Product access is Business-scoped.

Suggested permissions:
- products.view
- products.import
- products.review_mapping
- products.manage_media
- products.preview
- products.approve_ai
- products.generate_ai
- products.retry_ai
- products.request_sync

Owner-only operations remain outside ordinary Product permissions where appropriate.

All permission-sensitive actions must be checked server-side.

## 27. Training / tutorials relation

Training content is not part of Product state.

However, onboarding should be able to guide customers through Product workflows:
- recommended source structure
- mapping
- media management
- preview
- AI approval
- sync behavior

Tutorial content itself belongs to a separate Tutorial/Knowledge domain so Product remains compact.

## 28. Payments relation

Payment records are not part of Product state.

Product processing can be gated by subscription status and entitlements derived from the Subscription/Billing domain.

No Product mutation should directly modify billing records.

## 29. Import Preview / Sync Diff

Before a high-impact import/sync, the system should be able to summarize:
- new products
- changed products
- missing products
- ambiguous products
- blocked rows
- high-risk changes
- media changes

Example:

`+27 new, ~84 changed, -12 missing, ⚠5 ambiguous, ❌3 blocked`

This is especially important before large/bulk processing.

## 30. Identity evidence

For every non-trivial identity resolution, keep compact explainable evidence.

Examples:
- explicit ID matched
- SKU matched
- barcode matched
- brand/model matched
- deterministic fingerprint matched
- similarity score
- conflicting fields

Evidence should be compact and retained according to audit/retention policy.

## 31. Deduplication

Potential duplicate products must be identified separately from ordinary change detection.

Possible outcomes:
- no duplicate evidence
- possible duplicate
- confirmed duplicate after review

Automatic merging is disallowed when confidence is insufficient.

A future merge workflow must preserve publication history and clearly identify the surviving Product identity.

## 32. Error isolation

One malformed product must not corrupt unrelated products.

One customer/source failure must not block other tenants.

One platform publication failure must not corrupt Product state.

One AI failure must not change source facts or mark a valid Product as broken.

## 33. Resource efficiency

The starting deployment may run on a weak server.

Product Domain must therefore prefer:
- compact normalized state
- hashes/fingerprints
- references instead of duplicated payloads
- bounded history
- no full source snapshot on every sync
- no full rendered post copies unless operationally justified
- disposable cache
- cleanup/retention policies

Critical state must remain durable even if cache is lost.

## 34. Required Product Domain invariants

1. Row number never identifies a Product.
2. Row order never identifies a Product.
3. Product ID is immutable.
4. Product facts are independent of AI content.
5. Product is independent of Post/Publication.
6. Missing source data is not immediate deletion.
7. Ambiguous identity never silently merges.
8. Repeated identical sync is idempotent.
9. Invalid rows cannot corrupt valid rows.
10. AI never silently modifies canonical facts.
11. Historical Preset/AI versions are not silently rewritten.
12. Critical Product/publication state is durable, not cache-only.
13. Cross-business Product leakage is impossible.
14. Permissions are enforced server-side.
15. Unknown states must remain explicit until resolved.

## 37. Observability requirements

For Product operations, structured logs should be able to answer:
- tenant/business
- source
- source_record
- product
- mapping version
- product version before/after
- identity decision
- evidence summary
- changed fields
- risk level
- job/correlation ID
- actor
- result
- error category
- recovery action

Secrets and unnecessary source contents must never be logged.

Product Domain v2 is ready for foundation implementation only when:
1. Product identity strategy is approved.
2. Source Record model is approved.
3. Identity resolution and ambiguity policy are approved.
4. Missing/reappearing/deleted product policy is approved.
5. Product version/storage strategy is approved.
6. Custom field strategy is approved.
7. Product Media model is approved.
8. AI artifact relation/reuse rules are approved.
9. Business Type change behavior is approved.
10. Subscription/entitlement boundary is defined.
11. Product permissions are approved.
12. Failure matrix has deterministic outcomes.
13. Critical tests are defined.

## 40. Design principle summary

The Product Domain should be boring, deterministic and durable.

It should not try to solve every downstream problem.

Its job is to answer one fundamental question reliably:

"What product does this source record represent, what are the currently trusted facts about that product, what changed, and how confident are we?"

Everything else — AI rendering, platform-specific publication, remote message state, billing, tutorials and user-interface behavior — should consume this domain through explicit contracts.
